# 27B 主导的 LIBERO harness

27B 始终收到完整任务、双相机图像和实测状态，自己选择观察、动作及完成度查询。动作仍走原适配器的校验和控制器，成功仍由 LIBERO 原生判定。新版从 `eta0-run` 或 `deploy/run_libero.py` 进入。

## 默认行为与消融

| 角色 | 默认 | 何时调用 | 输出 |
|---|---|---|---|
| planner | 开 | 长任务第一次请求 27B 前，一次 | 最多 3 个结果级里程碑，合成一句，保留目标物、参照系和顺序 |
| supervisor | 开 | 连续停滞后、下一次 27B 决策前 | 基于抽帧、执行反馈及环境回执的一条建议 |
| teacher | 关 | 独立开启后，在同一停滞点触发 | 一个“可见线索 → 高层技能 → 预期结果”的假设示例 |

计划保留在后续上下文，纠正建议和示例只注入下一次决策。上层没有停止、推进子任务或派发物理动作的接口。格式错误、请求失败或上层预算耗尽时，执行器继续。上层如果仍输出澄清问题，系统向执行器提供当前环境回执，并记录问题。环境能回答目标条件是否满足，物体被遮挡等视觉识别问题仍由执行器处理。

默认将至少含两个原生目标条件的任务视为长任务。130 项中有 20 项符合，包括 LIBERO-10 的 9 项和 LIBERO-90 的 11 项。单目标也可能很难，针对特定任务可传 `--task-length long|short`。独立开关覆盖 `--mode` 预设。以下是单 episode 的角色参数，可以直接附加在相同的 suite、task、initial-index 命令上。

| 条件 | 参数 |
|---|---|
| 仅 27B | `--mode base` |
| 仅初始规划 | `--mode base --planner` |
| 仅停滞监督 | `--mode base --supervisor` |
| 仅停滞示例 | `--mode base --teacher` |
| 默认组合 | `--mode judge` |
| 全部开启 | `--mode teacher` |

两组比较时可以固定 `--instruction-mode revised` 和 `--completion-query`。新批次的 base 默认使用同一控制循环并关闭三个角色。需要复现原实现时，配对入口可选 `--upstream-base` 使用冻结的上游循环；它没有完成度工具。已有批次的续跑使用其冻结设置。角色组合写入 manifest 和每条 run.json。

## 停滞依据

- 连续 3 个有失败证据的结果触发一次介入。计入动作被拒、原生成功仍为假的 finish、零 tick 的执行及控制器报告的中断、错误或跟踪滞后。正常的视觉查询和完成度查询不增加计数。
- 对有完整逐条件回执的动作，若没有新增已满足条件，比较最近 24 个动作的实测末端位置、朝向和开度。相近构型须出现三次，所选样本两两相邻至少隔 8 个物理动作。构型容差为 8 mm、8° 和 3 mm。缺失或部分未知的回执清空这一窗口。
- 独立检查控制器位置误差。至少执行 16 个动作后，若最近 8 个动作都返回有效的 `path_complete` 位置误差，且其中至少 3 个（含当前动作）达到 30 mm，就请求一次监督。该分支可在缺少分项完成度时工作。连续 8 个有效的小误差动作后才允许它再次触发。确认新目标条件得到满足时，清空累积证据并重新计数。视觉查询不会增加物理动作数。
- `--stall-failures` 控制连续失败次数，`--stall-plateau` 控制构型样本间距。构型与位置误差两个窗口使用不同证据；调节构型间距不影响位置误差阈值。阈值选择、旧轨迹抽帧及按任务留出的复核结果见[原 harness 监督触发审计](stall-audit.md)。

## 分账与测量

27B 保留每条 2,700 秒、360 次执行器决策和 120 个物理动作的预算。环境及上下文处理计入底层墙钟。上层默认另计 900 秒，最多 8 次逻辑请求，包含角色之间的全部调用。每个请求继续沿用最多 4 次网络重试。重试退避、读图打包、错误和超时占上层时间。批量运行的外层看门狗为两份预算及清理预留时间。

| 输出 | 统计口径 |
|---|---|
| `calls` / `actions` | 收到回复的执行器决策数 / 已执行物理动作数 |
| `lower_chat_calls` / `lower_chat_s` | 27B Chat Completions 请求数及客户端等待时间，含上下文压缩调用、服务排队 |
| `lower_wall_s` / `upper_wall_s` | 环境初始化至评分的底层墙钟 / 上层累计墙钟，两者之和为 `episode_wall_s` |
| 批次行的 `elapsed_s` | 仿真子进程启动至退出，含解释器启动与清理 |

## 语义包与仿真绑定

单独在仿真解释器安装本项目的 `libero` extra，例如从本仓库运行 `uv pip install --python "$SIM_PYTHON" '.[libero]'`。依赖固定在 OpenETA-Benchmark 的 `c39883cd94c3b413c19e048ab82317fc6e024fa1`。运行时同时检查 0.3.2 版本和包摘要，按 suite 与原生任务名解析，默认显式选择 revised。自定义 `--instruction` 优先，运行日志保存用户措辞、基准措辞及原生措辞。[固定版本的语义包](https://github.com/OpenETA7/OpenETA-Benchmark/blob/c39883cd94c3b413c19e048ab82317fc6e024fa1/src/openeta_bench/data/task_packs/libero/full-v1.json)

完成度工具需要带 Git 元数据的 LIBERO checkout，固定在 `8f1084e3132a39270c3a13ebe37270a43ece2a01`。单条及批量入口接受 `--libero-source-root PATH`，单条还可读取 `ETA0_LIBERO_ROOT`。入口在导入模拟器前选择该 checkout，并写 episode 私有的 LIBERO 路径配置，让实际运行的源码、BDDL 及资产来自同一位置。11 月 23 日只读核对了旧云端快照，语义包引用的 277 个文件摘要全部一致，但其目录缺少 Git 元数据，解释器也尚未安装 OpenETA-Benchmark。未来恢复云测前需准备独立的固定 checkout 和依赖。[固定版本的 LIBERO](https://github.com/Lifelong-Robot-Learning/LIBERO/tree/8f1084e3132a39270c3a13ebe37270a43ece2a01)

在已有环境的每个物理动作内，官方适配器观察原生评估并封存 `native_goal_conditions_v1` 回执。执行器发送 `{"stage":"check_task_completion","observation_id":"当前观测 ID"}` 读取最新结果。重复读取不推进物理，也不额外运行评分，并与视觉查询共享每观测 4 次上限。reset 后可以得到 pending，叶条件缺证据时可以是 null。主动查询和提前 finish 的回执保存在 events.jsonl。提示词消融可选 `--instruction-mode original`，工具消融可选 `--no-completion-query`。

27B 自己决定何时查询、如何解释条件和下一步动作。条件的名称、描述、数量和满足状态由适配器提供。查询本身不会请求上层监督。单项任务和多项任务共用这一协议，普通观测只带图像和实测状态。其他 benchmark 可通过适配器的 `completion` 属性提供缓存回执；缺少此能力时，工具从执行器提示中省略。

要单独比较查询工具的收益，固定初态、指令、预算，在 `--mode base` 下切换 `--completion-query` / `--no-completion-query`，覆盖多类任务。单条和批量入口都支持该开关，批量比较将相同设置传给使用新 harness 的各组。关闭开关也会关闭该适配器的回执采集，有监督的配置会同时改变监督者可见的证据。`RESULT.json` 和批次记录中的 `completion_queries` 只统计执行器实际发起且获准的进度查询；`queries` 是单条结果中包含视觉查询的总数。

## 首版触发规则在 532 条旧轨迹上的记录

按原始事件顺序抽取了 40 个任务、532 条已返回轨迹，共 14,541 个可定位的执行器决策。489 条至少有一次执行器回复，另外 43 条未到达可回放的决策。回放使用生产代码的调度器，上层由本地记录器代替。规划仅在有首个决策时计数；原轨迹最后一次决策之后不追加假想动作。

| 轨迹来源 | 轨迹数 | 曾进入执行器 | 初始规划 | 仅凭直接记录的失败，监督次数 | 加入单条件还原，监督次数 |
|---|---:|---:|---:|---:|---:|
| 原 harness | 133 | 133 | 30 | 11 | 32 |
| Qwen4 Max | 132 | 111 | 25 | 6 | 23 |
| DeepSeek Flash | 133 | 114 | 25 | 2 | 21 |
| Kimi K3.1 Pro | 134 | 131 | 30 | 2 | 7 |
| 合计 | 532 | 489 | 110 | 21 | 83 |

旧轨迹没有逐条件回执。第一种回放仅使用已记录的拒绝、finish 和控制器反馈。第二种利用执行循环进入下一次决策前已检查原生成功这一事实，对恰有一个目标条件的任务，可还原该条件当时为假；再结合实际记录的末端姿态和夹爪开度检查是否反复回到同一构型。多条件任务的部分完成状态保持未知。两种回放各自执行完整的去重逻辑，触发数不能逐项相加。

在原 harness 的 133 条轨迹上，第二种回放会对 41 条最终失败中的 16 条给出建议，也会对 92 条最终成功中的 15 条给出建议。25 条失败仍无触发。这些比例描述规则选择在哪些轨迹介入。阈值是工程初值，没有在独立轨迹集上优化。

具体到开炉灶任务（libero_goal / 07，初态 1），原 harness 的 9 次决策中两个上层角色均未触发。沿旧 Qwen 轨迹，首次监督发生在第 13 个动作之后、第 16 次决策之前；旧 Qwen 在这条轨迹累计调用上层 21 次。黄油入篮任务（libero_object / 06，初态 0、1）沿旧 DeepSeek 轨迹均未触发监督，新控制循环也不给 supervisor 终止 episode 的权限。回放无法观测新建议后的动作、成功率和实际延迟。

这两份 JSON 保留首版回放结果，用作调整规则的固定对照。当前规则的重放命令与含终点残差的输入见[原 harness 监督触发审计](stall-audit.md)。
